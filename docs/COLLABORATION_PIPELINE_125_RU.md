# Совместная разработка и перезапуск — состояние после изменений 125

Изменения внесены непосредственно в исходники MaRed. Готовый мод и архив патча не выпускаются. Внутренняя версия genesis-core: 0.1.41.

Дальнейшие изменения: [инструменты 126](WORKSPACE_TOOLS_126_RU.md) добавили импорт папки, заготовку мода, поиск, сравнение и встроенный Wrapper. Ниже сохранено описание этапа 125.

## Как проходит работа

1. Сервер хранит проекты Workspace в мире, в `genesis/workspaces122`. У каждого проекта есть владелец, участники, права и журнал. Клиенты отправляют изменения CRDT; сервер проверяет личность, права, идентичность файла и выделенные диапазоны операций. Другие участники получают текст, цветные курсоры, выделения и отметки редактирования.
2. Текущий текст и утверждённый релиз разделены. На экране проверки выбираются изменения, затем выполняются предварительный просмотр и утверждение конкретного хеша. Для невыбранных изменений сохраняются ранее утверждённые версии. Поэтому утверждение одного файла не означает удаления остальных файлов из релиза.
3. Новая кнопка **«Собрать / публикация»** загружает утверждённые исходники на компьютер разработчика. Сервер проверяет права BUILD/READ и видимость CODE/BUILD для всего снимка при каждом запросе. Передача идёт блоками по 12 КиБ. Клиент проверяет порядок, длину, SHA-256 файлов и общий хеш с ревизиями. Потерянные ответы на эти чтения повторяются ограниченное число раз.
4. Для каждой сборки создаётся новая папка `genesis/workspace-builds125/approved125-…/project` внутри каталога клиента. Старые результаты и чужие исходники в неё не подмешиваются. Рядом сохраняется манифест `workspace125`; он не входит в исходники Gradle. Это локальная проверка целостности, а не подписанное разрешение на установку.
5. Пользователь указывает локальный JDK, папку/файл Gradle Wrapper и задачу. Пути инструментов запоминаются. Запуск Gradle подтверждается явно: скрипты выполняются с правами пользователя. Используется существующий GradleBuildRunner: ограничение времени, остановка дочерних процессов, захват вывода, проверка изменения входов и отчёт о результатах. При первой сборке реального NeoForge-проекта могут потребоваться загрузки зависимостей.
6. После успешной сборки выбирается конкретный мод, повторно проверяются утверждённый релиз и права на сервере, а локальные исходники сверяются с загруженным снимком. Создаётся BuildSnapshot84 с происхождением сборки, хешами артефакта, отчёта и зависимостей. Изменение исходников после сборки делает снимок недействительным. Выбранная при старте задача сохраняется независимо от дальнейшего редактирования поля.
7. Открывается существующий экран публикации: выбор стороны CLIENT/SERVER/BOTH, полный состав на основе baseline, предварительный просмотр, подпись релиза. При наличии выбранной папки сервера используется её контроллер `.genesis/server104`. Подписывать и применять релиз по-прежнему должен владелец установки сервера; членство в Workspace не выдаёт доступ к файловой системе чужого компьютера или ключу публикации.
8. Из публикации открывается управление обновлением существующей папки сервера. Подготовка/предложение → согласия клиентов → подтверждённая подготовка → COMMIT → сохранение и остановка сервера → замена утверждённых JAR → запуск через настоящий `run.bat` → проверка нового процесса и допуска → возврат обновлённых клиентов. Эта часть использует существующий FolderRollout118 и проверки связей 120.

Новые серверные операции BUILD_SOURCE/BUILD_CHUNK являются чтением. Они не запускают Gradle на сервере и не устанавливают моды. Новые неутверждённые правки могут продолжаться параллельно сборке предыдущего утверждённого снимка. Новое утверждение, смена прав или потеря соединения останавливают дальнейшую подготовку старой сборки через этот экран.

## Что нужно для доставки мода всем участникам

- Управляемый сервер, актуальная версия MaRed у сервера и клиентов и рабочий внешний контроллер клиента для замены JAR и запуска следующего процесса игры.
- Исходники полноценного Gradle-проекта в утверждённом снимке: build/settings, свойства, Java, metadata и необходимые текстовые ресурсы. Один файл Java сам по себе не превращается в мод.
- Первичный полный baseline клиента и сервера, ключ подписи, выбранная публикация, доступный клиентам HTTPS и подтверждение доверия к ключу.
- Для удалённого администрирования — проверенная учётная запись/настройка аутентификации и права Maop. Права Workspace и права управления сервером проверяются отдельно.
- Явное согласие каждого участника обновления. Принявшие участники должны подготовиться; COMMIT остаётся явным действием администратора. Отказавшийся, отсутствующий или неподготовленный клиент не считается успешно обновлённым.

Исправлена гонка порядка сетевых сообщений: нажатие «Принять» теперь сохраняет локальное намерение, даже если настройки контроллера приходят позже. Согласие привязано к instance/round/ticket/release/distribution, адресу, endpoint, ключу, хешу и ревизии. Чужое предложение не получает это разрешение; отмена очищает его. Отдельного повторного согласия из-за порядка сообщений не требуется. Повтор после ошибки остаётся явным.

## Обычный перезапуск без замены клиентских модов

Раньше локальная кнопка готовила возврат только администратора. Для owner104 добавлена отдельная подписанная команда RESTART125: она сохраняет мир, уведомляет всех подключённых клиентов с новым каналом и затем штатно останавливает сервер. SHUTDOWN остаётся отдельным действием без обещания возврата.

Клиент запоминает текущий ServerData и после отключения подключается к тому же адресу. Ожидание можно отменить. Повторное уведомление с тем же request игнорируется. Обычная потеря сети или остановка без уведомления не запускает автоматический возврат. Механизм не закрывает JVM клиента и не устанавливает JAR; для обновления модов используется цепочка согласия и подписанного COMMIT выше.

Автоматические попытки ограничены существующим RestartReturn108: после 30 секунд ожидания предлагается продолжить, а не бесконечно переподключать игрока. Возврат к миру учитывает экран загрузки и показанные кадры. Клиенты старой версии без канала RESTART125 уведомление не получают. Ручной запуск изменённого BAT без управляемого контроллера и старый legacy-owner74/75 не приобретают этот новый маршрут автоматически.

## Сценарии проверки

Новые WorkspacePipelineChecks125 проверяют реальный hub/журнал и передачу: отсутствие утверждения, пустой файл, Unicode и несколько блоков, неправильный путь/смещение/размер/хеш, незавершённый снимок, traversal, Windows-коллизии путей, новую отдельную папку, повторное чтение после потери ответа, смену утверждения между блоками, отзыв прав, VIEWER, скрытый исходник, восстановление hub из журнала и привязку согласия к точному предложению.

WorkspaceBuildProcessChecks125 использует настоящий установленный Gradle и JDK: передача → материализация → компиляция Java и упаковка metadata/resources → BuildSnapshot84 → проверка → отказ после изменения исходника. Это небольшой тестовый мод без запуска Minecraft. Gradle используется из уже имеющегося кэша; тест не выдаёт сетевую загрузку за проверку offline-сборки.

Повторяются проверки CRDT, конкурирующих редакторов, stale leases, истории/удаления, частичного утверждения, публикации/подписей, согласия/COMMIT, сохранения мира, запуска/отката, TLS, допуска клиентов и реального Windows BAT. ## Практические границы и следующая работа

Игровая приёмка на двух настоящих клиентах и сервере остаётся необходимой: отрисовка курсоров, нажатия в новых экранах, доставка уведомления перед отключением, внешняя авторизация лаунчера и возвращение обоих игроков в мир. Автотесты процессов и подписанных протоколов эту проверку не заменяют. Пользовательский сервер и его мир в этом прогоне не запускались.

Нынешний Workspace ориентирован на текст: 64 файла проекта и 8192 кодовых точек на документ. Для больших проектов нужны отдельно спроектированные лимиты, импорт дерева и передача бинарных ресурсов. Совместные PNG/модели, личный undo по автору, комментарии к изменениям, восстановление расположения вкладок и автоматическая архивация большого журнала ещё не завершены. Сборка доступна для уже заполненного Gradle-проекта; мастер массового импорта/создания проекта в общем Workspace следует добавить отдельно.

Изменение собственного bootstrap-мода MaRed через эту публикацию по-прежнему запрещено BuildSnapshot84: замена механизма управления требует отдельного безопасного обновления. Обычные разрабатываемые моды проходят существующий маршрут публикации.
