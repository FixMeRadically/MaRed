Это находки по коду. Длительность на Windows и причинность для каждой конкретной прошлой попытки отдельно не подтверждены. На этом проходе рабочий код не менялся. Ручной аудит остальных подсистем продолжается.

### Workspace и Blockbench

- `WorkspaceHub122.java`, `WorkspaceServer122.java`: экспорт выполняется под общей блокировкой Workspace и в очереди I/O. Он записывает снимок и перечитывает экспорт для проверки. Большой экспорт может задержать обработку правок и курсоров. Перед переносом дисковой работы из критической секции нужно зафиксировать неизменяемый снимок и проверить права на момент его выдачи. Фактическая задержка курсоров ещё не измерена.
- `DesktopBlockbenchScreen148.java`: при каждом открытии экрана скрипт плагина записывается поверх локальной копии. Запись проходит в фоновом потоке, но её прерывание может оставить неполный файл. Кандидат на атомарную замену при изменении содержимого.

### Как завершается обновление выделенного сервера

- `automatic156.py`: автоматический сценарий заканчивает свою работу на `COMMIT_QUEUED`. Это означает, что запрос поставлен в очередь. Сценарий не ждёт запуска нового поколения, входа игроков или закрытия раунда.
- `folder118.py`, `inplace104.py`: `finish()` вызывается по отдельной команде `CLOSE`. Обычный `SHUTDOWN` её не вызывает, поэтому состояние `ACTIVE_UPDATED` остаётся в журнале после успешной остановки. При следующем запуске оно приводит к `FOLDER118_INTERRUPTED_ROUND`. Это совпадает с наблюдаемой последовательностью на Windows.
- `remote70.py`, `control73.py`: после входа клиент отправляет `JOINED`, но результат проверки подтверждения не используется. Если сервер не подтвердит квитанцию, игрок может быть в мире, а серверный счётчик входов останется неполным. Это отдельный риск для автоматического закрытия по счётчику. В присланных журналах он не подтверждён.
- `inplace104.py`, `folder118.py`: в устойчивом состоянии обновлённого сервера формирование статуса и один heartbeat могут вызвать `target_ready()` суммарно трижды. Фоновый опрос вызывает её дополнительно. Каждая успешная проверка перечитывает набор модов для хеширования. Число вызовов следует из кода, время на Windows не измерено.

Для этапа исправлений нужны проверки: закрытие после подтверждённого входа всех участников, отсутствие автоматического закрытия при неполных подтверждениях, повторное закрытие после потери ответа, обычная остановка и следующий запуск. На этом проходе изменения только в отчёте.

Итог: охват расширен на раздачу, допуск, права, восстановление, серверное хранение и синхронизацию Workspace. Полный аудит в реальном Minecraft остаётся открытым. Цифры времени из локального стенда не отражают время на сервере пользователя.
