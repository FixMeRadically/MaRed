# Genesis118: связанный серверный переход

Это большой интеграционный патч, а не утверждение о полной готовности0.4.5.

## Действующий путь

Script -> BuildSnapshot84 -> ScriptPublication84 -> Publication79/83 -> FolderUpdateScreen118
-> DedicatedAdmin75/ServerAccess88/Maop113 -> Owner104/FolderRollout118 -> RemoteConsent72
-> ControlRoom73 COMMIT -> QUIESCE -> immutable CommitFence81 -> внешний control pump
-> INSTALLED от всех включённых участников -> SAVE_STOP + matching final receipt + empty Job
-> Changes104 -> runtime READY -> admission/25% -> JOINED.

Сервер остаётся в своей папке. Копий мира/поколений сервера адаптер не делает.
Сохраняются только изменяемые JAR и подписанный журнал. Клиентские исходные профили
по-прежнему сохраняются: Remote70 работает через новую клиентскую копию.

Сервер без клиента использует тот же Owner104 и модульfolder118. Клиент нужен только
для игровой панели; права команд могут выдаваться серверной консолью черезMaop113.
ОбычныйOP не превращается в право публикации/COMMIT. Offline-режим разрешён только
для локальной проверки с loopback-подключениями, не как удалённая аутентификация.

## Пользовательские входы

- Сервер -> продвинутые настройки -> Обновление игроков.
- Script -> Собрать для сервера -> Создать выпуск для игроков.
- Подготовить выпуск/HTTPS используют существующие встроенные экраны, не новый CMD.
- Владелец один раз выбирает подписанную базу, точно совпадающую с работающим сервером.
  Затем новый выпуск предлагается игрокам. COMMIT доступен после решений и подготовки.
- Создание подписи не является применением. До COMMIT отмена возвращает прежний указатель.

Первичная настройка доверенной HTTPS-точки/сертификата и полных клиентского/серверного
наборов всё ещё нужна. Она не объявлена автоматической установкой интернета/сертификатов.

## Согласование и восстановление

Java читает source/target session и receipt из точного HMAC-связанного launch-канала.
Никакого поиска подходящего PID или доверия открытому порту. Подготовленный набор
связан с архивом, release, inventory, generation и Changes104 plan SHA. Изменение
подготовленных JAR до COMMIT отклоняется. Клиентский-only выпуск имеет отдельную
подписанную квитанцию неизменного серверного набора, без фиктивного changed JAR.

После раннего сбоя нового сервера, до маркера загрузки мира, старые JAR восстанавливаются
и выполняется ровно одна попытка старого запуска. При возможном изменении мира или
неподтверждённом выходе процесса остаётся RECOVERY_REQUIRED/WAITING_FOR_STOP.
При смене владельца незавершённый сетевой COMMIT не повторяется. Локальное подтверждение
восстановления проверяет сохранённую привязку, точный набор и подписанную пару и закрывает
старые разрешения; старые run-bound permits не переносятся.

После сбоя серверного выпуска клиентский Remote70 пока сообщает отмену/ошибку и хранит
старый профиль. Автоматический запуск старого клиентского профиля НЕ реализован118.
Это остаётся отдельным незавершённым звеном, а не скрытым обещанием отката всех устройств.

## Подтверждение изменений

Фоновая нативная сборка раньше могла сама создать review и немедленно применить его.
Теперь она показывает подтверждение конкретного набора, повторно проверяет исходники
и передаёт тот же immutable review в stageSet99. Устаревший stage без review отклоняется.
Script/manual/watch, Server115 review и подпись пары используют свои проверки неизменного
артефакта. Это не единый доказанный gate всех низкоуровневых CLI: этот аудит ещё открыт.

## Исторический код

UpdateMachine35, Waiting/PlayerUpdate и стенды36–57 сохранены для диагностики и проверок.
Они не подключаются параллельно к владению тем же миром. Старые страницы66/103 заменены

## Сборка

Core compileJava использует полный sourceSet с incremental=false; проверяются реальные
входы задачи и ключевые выходные классы. Это исправляет обход исходников при частичной
компиляции и даёт точную диагностику. Успех полной Gradle/JDK21 сборки нужно подтвердить
на целевой машине: здесь доступен только JDK17, нет Gradle/NeoForge/Windows/Minecraft.
