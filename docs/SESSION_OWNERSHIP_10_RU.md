# MaRed / Genesis — session-ownership-10

Накопительный патч поверх 05, 06, 07, 08 или 09. Исправляет завершение supervisor и повторную активацию; включает анимацию Core и быстрый запуск из 09, функционал фонового применения из 08 и прежние lifecycle/world-profile изменения.

## Что было найдено

По пользовательскому журналу сборка chatimagefix завершается успешно, а применение останавливается на занятом порту 27670. Сам журнал не определяет точную причину оставшегося процесса. В коде 09 воспроизведён конкретный дефект: когда настоящая игровая JVM завершилась, но её launcher/оболочка продолжает работать, supervisor продолжает ждать launcher и остаётся RUNNING. Отдельная тестовая JVM имитирует такую оболочку; это воспроизведение архитектурной проблемы, а не запись настоящего Windows/Gradle сеанса пользователя.

Также исправлены гонки закрытия/перезапуска, незавершённой передачи управления и блокировка lifecycle синхронным выводом логов.

## Исправления

- Supervisor отдельно учитывает реальную игровую JVM: PID, время старта, состояние и монотонную последовательность heartbeat. Сигнал создаётся при загрузке MaRed и обновляется независимо от кадров, игрового тика и HTTP.
- Есть отдельные отметки начала закрытия Minecraft и выхода JVM. Watchdog проверяет игровую сессию, даже пока Gradle/оболочка живы. При подтверждённом конце игры оставшаяся оболочка убирается, контроллер освобождает порт, окно, собственные runtime-файлы и lock.
- При доступном OS API сравниваются PID и время старта. Задержанный heartbeat не завершает живую JVM с той же идентичностью: долгий GC/задержка диска сами по себе не принимаются за выход игры.
- Когда ОС скрывает metadata, используются ограниченные таймауты и сигнал выхода. При неоднозначном таймауте автоматический повторный запуск baseline отключён, чтобы не создать второй клиент поверх непроверенной JVM.
- Запрос HTTP restart относится к конкретному launchId. Запрос старой JVM, restart после начала обычного закрытия и повторная обработка одного выхода отклоняются.
- Обычное закрытие не вызывает повторного запуска. Подтверждённый crash пробного мода сохраняет ограниченное восстановление предыдущего JAR: одна baseline-попытка, затем завершение при повторной ошибке.
- Передача управления стала двухфазной: новый supervisor привязывается к порту и сообщает точную идентичность; текущий клиент явно подтверждает handoff; только после этого supervisor ждёт выхода исходной JVM и запускает следующую. Неподтверждённая/отменённая активация не запускает игру позже сама по себе.
- Задача закрытия клиента, которая не успела выполниться до отмены handoff, больше не может закрыть игру спустя время. Ошибки активации завершают future и освобождают ACTIVATING.
- Проверка занятого порта происходит до замены сохранённых token/instance/config. Проверяются служба, lifecycle version, instanceId, путь config и порт. Старый владелец без активной игры может быть завершён через его защищённый API; активация дожидается освобождения и порта, и config lock. Активная игра или чужая служба не останавливаются.
- Отдельный activation.lock сериализует конкурирующие активации одного проекта. Bootstrap JAR имеет имя с UUID активации, поэтому новая активация не пытается перезаписать JAR, который Windows ещё держит открытым у прежней JVM.
- HTTP listener закрывается независимо от завершения lifecycle worker и ожидания дерева процессов. Ответ принятого запроса получает ограниченное время на отправку. Необработанные lifecycle-ошибки тоже переводят контроллер к завершению.
- Логи пишутся через ограниченную неблокирующую очередь. Застрявший stdout/файл лога не удерживает lifecycle и HTTP; хвост остаётся в памяти. При переполнении очередь теряет часть диагностического вывода и сообщает об этом, вместо зависания игры/контроллера.
- Cleanup учитывает прерывание потока; наблюдатель не прерывает сам себя при закрытии. Проверенный reuse PID не блокирует очистку, а непроверенный живой потомок блокирует второй запуск и не уничтожается наугад.
- После освобождения ресурсов standalone bootstrap завершает собственную JVM. Это действие не выполняется внутри Minecraft. Убрана зависимость выхода контроллера от оставшихся служебных потоков/AWT.
- Клиентские telemetry-запросы переиспользуют HTTP client вместо создания отдельного на каждую отметку.

## Установка

Закрой Minecraft и старый supervisor. В этом случае ты уже освободил порт вручную; перед установкой ещё раз закрой тестовую игру.

Распакуй архив и запусти `apply.cmd` для прежнего пути проекта. Либо из папки комплекта:

```powershell
py .\patch\apply_changes.py "$env:USERPROFILE\Desktop\MappetPort\MaRed" --check
py .\patch\apply_changes.py "$env:USERPROFILE\Desktop\MappetPort\MaRed"
```

Затем из MaRed на JDK 21:

```powershell
.\gradlew.bat --stop
.\gradlew.bat clean build
.\gradlew.bat runClient
```

Важно пересобрать и основной мод, и вложенный supervisor-bootstrap: `clean build` делает это вместе. Уже запущенная старая JVM не обновится от замены исходников.

Установщик проверяет все затронутые файлы до записи, сохраняет резервную копию и отказывается заменять неизвестные локальные правки. Этот этап меняет DevActivationService, поскольку ошибка занятого порта исправляется именно на пути активации. Сохранённые `command.N`, `workDir`, порт и остальные настройки пользователя во время активации сохраняются.

Для отката при закрытых игре и supervisor:

```powershell
py .\patch\apply_changes.py "C:\путь\к\MaRed" --restore "C:\путь\к\MaRed-supervisor-backup-..."
```

## Проверка у себя

1. Запусти игру после clean build, войди в одиночный приватный мир и примени изменение chatimagefix. Проверь возврат в мир и исчезновение анимации после готовности.
2. Закрой Minecraft обычным способом. Через несколько секунд проверь:

```powershell
Get-NetTCPConnection -LocalPort 27670 -State Listen -ErrorAction SilentlyContinue
```

Пустой вывод означает, что порт свободен. При обычном быстром выходе освобождение не должно ждать окончания жизни Gradle daemon. Если JVM ещё сохраняет мир/выполняет shutdown hooks, контроллер дожидается её реального выхода; он не принимает активное закрытие за уже завершённый процесс.

3. Снова запусти игру из IDE/Gradle и примени мод. Повтори обычное закрытие и новый запуск 2–3 раза. Ручная очистка порта не должна требоваться.
4. Проверь ручной restart отдельно от обычного закрытия: перезапуск возвращает игру; обычное закрытие заканчивает сессию.
5. Если проблема остаётся, нужны `run/client/config/mared/dev/logs/supervisor.log`, `bootstrap.log` и момент закрытия игры. Новый `/status` содержит lifecycleVersion 10, gamePid и gameState — они помогают отличить игру от launcher. Не публикуй supervisor.properties: там хранится управляющий token и могут быть приватные launch arguments.

Автоматическое освобождение старого владельца применяется к этой версии lifecycle. Оставшийся старый контроллер 05–09 без нового identity API может потребовать однократного ручного завершения; неизвестная служба не останавливается по одному номеру порта.

## Дополнительные таймауты

Необязательные ключи в `run/client/config/mared/dev/supervisor.properties`:

```properties
session.startupTimeoutMs=900000
session.leaseTimeoutMs=120000
```

Первый ограничивает launcher, у которого MaRed так и не зарегистрировался. Второй — потерю heartbeat, когда OS metadata недоступна. Это не обычное время ожидания после закрытия игры. При доступной идентичности живого процесса heartbeat-таймаут не завершает его. Внешнее окно Core и fastLaunch по-прежнему управляются настройками 09.

## Проверки

`py .\verification\run-checks.py` запускает JDK-only/adapter проверки на полном JDK 17+; реальный MaRed требует JDK 21. Результаты находятся в `verification/*-checks.log`.

Добавлены: воспроизведение зависания 09 на game/launcher JVM; normal exit, Runtime.halt, launcher без регистрации, непрочитанный stdout, многократное использование одного порта; отказ завершать активную/чужую сессию; восстановление после закрытия; защита launchId и closing/restart race; unchecked lifecycle failure с прерыванием worker; неблокирующий логгер; actual DevActivationService и helper на отказах; отмена поздней задачи закрытия. Используются реальные процессы, HTTP, файлы и блокировки; Minecraft/NeoForge API в клиентских adapter-тестах явно подменён.

Полный Gradle/NeoForge build, настоящий Minecraft и Windows process-tree/JAR-lock поведение здесь не выполнялись. Успешный исходный handoff и descendant-тесты отмечены SKIP, если среда скрывает ProcessHandle metadata. Новый двухфазный commit дополнительно проверяется на уровне решения, а отказ небезопасного handoff — настоящим bootstrap-процессом. Проверки не являются обещанием отсутствия любых ошибок на непроверенной платформе.
