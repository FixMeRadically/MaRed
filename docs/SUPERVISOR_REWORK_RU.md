# Supervisor: надёжный жизненный цикл (поверх приложенного MaRed)

> Это описание первого патча. В menu-02 F9 заменена панелью MaRed → «Режим разработки», добавлен автовозврат на сервер. Актуальные действия: SUPERVISOR_MENU_02_RU.md.

## Что исправлено

В приложенном MaRed находились более ранние версии, чем в описании: Supervisor.main закрывался на EOF; ActivationService использовал cmd /c start, необслуживаемый stdout и classpath игрового загрузчика. Не было проверки принадлежности HTTP-сервиса, ожидания выхода исходного Minecraft перед первым запуском и последовательной обработки команд.

Теперь supervisor остаётся в пакете com.fixmer.genesis.supervisor внутри мода. Отдельного Gradle-проекта нет. Сборка мода автоматически упаковывает те же JDK-only классы в приватный ресурс mared/dev/supervisor-bootstrap.jar. Кнопка извлекает его в config/mared и запускает обычный java без cmd /c start. Это внутренний bootstrap, не отдельный устанавливаемый мод или проект. Требуется заново собрать мод: замены одних Java-файлов без нового build.gradle недостаточно.

Передача управления:

1. Фоновый поток готовит конфигурацию и bootstrap. Главное меню остаётся отзывчивым.
2. Supervisor захватывает файловую блокировку своего конфига и HTTP-порт. Если порт занят, новый Minecraft не запускается.
3. Проверяет рабочую директорию, синтаксис конфига и доступность исполняемого файла.
4. Отвечает собственными protocol=2, instanceId, supervisorPid и WAITING_FOR_PARENT. Кнопка проверяет их с уникальным токеном.
5. Исходная игра вызывает Minecraft.stop() на клиентском потоке. Новый Minecraft запускается только после фактического выхода исходного PID.
6. Если исходный процесс не выходит за 60 секунд, supervisor переходит в ERROR и не запускает второй клиент. Если среда скрывает ProcessHandle, передача управления отклоняется до закрытия игры.

EOF больше не завершает supervisor. Все start/stop/restart выполняются одним lifecycle-потоком. Пока операция выполняется, повторные запросы получают 409; неконтролируемой очереди рестартов нет. Падение ребёнка не создаёт бесконечный цикл рестартов: ERROR виден через /status, можно исправить причину и повторить /start.

F9 и /mared dev restart используют POST /restart?cooperative=true, ждут именно 202 с ok:true и вызывают Minecraft.stop(). Прямой System.exit удалён: обычный выход Minecraft даёт штатному пути остановки сохранить мир и вызвать существующие обработчики состояния игрока. Команды dev перенесены в RegisterClientCommandsEvent и ограничены CLIENT: удалённый сервер или dedicated server не вызывают клиентский сервис перезапуска.

Обычный POST /restart из внешнего инструмента сам останавливает ребёнка, ему не требуется выход игры по F9. /status не блокируется на ожидании остановки. /status и /logs не публикуют команду запуска и токен управления.

## Первый запуск после установки

1. Закройте прежнюю игру и прежний supervisor. Старый процесс продолжает исполнять старые классы после замены файлов.
2. Примените patch/apply_changes.py к корню существующего MaRed. Патч создан именно для приложенного MaRed(1).zip. Архив Genesis-stage-07-6-command-editing использован как образец упаковки, его изменения сюда не примешаны.
3. Выполните .\gradlew.bat build под Java 21. Для запуска из проекта: .\gradlew.bat runClient. При установленном JAR замените старый JAR новым из build/libs.
4. Нажмите Enable Dev Mode. Ошибки отображаются в строке Status, а исходная игра при ошибке подготовки остаётся открытой.
5. Откройте тестовый мир. В dev-клиенте проверьте F9, затем /mared dev restart. Положение и прочее состояние обслуживают прежние классы шагов 3–5; они не переписаны этим патчем.

Старые command.N, workDir и интервалы из config/mared/supervisor.properties сохраняются. Если они были сгенерированы неудачно, сначала скопируйте этот runtime-конфиг, затем удалите только строки command/command.N и workDir для повторного определения. Патч сам не удаляет конфиги, миры и .genesis-dev.

Без ручной команды используется точный argv текущей JVM и фактический CWD. Видимые JDWP-аргументы убираются, чтобы не ждать отладчик и не занимать его порт повторно. Это повторный запуск уже собранных классов: компиляцию нужно выполнить отдельно. Если Windows/лаунчер скрывает argv, в распознанном исходном проекте MaRed используется gradlew.bat --no-daemon runClient (с компиляцией изменений, поэтому дольше). Вне проекта требуется явная команда; sun.java.command по пробелам больше не разбивается.

Для воспроизводимого dev-цикла из исходников можно сразу задать:

```properties
workDir=C:/Users/fixme/Desktop/MappetPort/MaRed
command.0=C:/Users/fixme/Desktop/MappetPort/MaRed/gradlew.bat
command.1=--no-daemon
command.2=runClient
```

Затем нажать кнопку: порт, токен и идентификатор экземпляра добавятся автоматически. В command.N каждый аргумент задаётся отдельно, без внешних кавычек. В .properties используйте прямые слеши Windows либо двойные обратные слеши. Файл читается и пишется как UTF-8. Относительные workDir/logFile считаются от директории конфига, а аргументы запуска — от workDir. При ошибке автоматического определения можно создать этот файл вручную до нажатия кнопки.

JVM @argfiles, пути classpath, временные файлы лаунчера и сессионные учётные данные должны оставаться действительными. Скрытый внутри @argfile JDWP не переписывается. При удаляемых launcher-файлах, авторизации или необходимости пересобирать код используйте явный runClient либо свою воспроизводимую команду. Переносимость команд всех сторонних лаунчеров не гарантируется.

## Конфигурация и диагностика

config/mared/dev.json теперь действительно JSON; прежний формат properties в этом файле также читается:

```json
{"controlPort": 27670}
```

Некорректный порт/JSON выдаёт понятную ошибку, а не молчаливый переход к другому порту. Enable доступна и при включённом marker-dev-режиме без supervisor. Поля статуса и кнопки перерисовываются; текст переносится по ширине окна. MaredDevKeybinds и MaredClientSetup оставлены с рабочей регистрацией F9 и логами QUICK-RESTART.

Логи относительно игровой config-директории:

- config/mared/supervisor-bootstrap.log — ошибки JVM, загрузки классов, блокировки и bind.
- config/mared/supervisor.log — события supervisor и вывод дочернего процесса (если logFile не переопределён).
- logs/latest.log — обычные логи Minecraft.

Для HTTP нужен заголовок X-Genesis-Token со значением controlToken из supervisor.properties; дочерняя игра получает его через GENESIS_SUPERVISOR_TOKEN. Все маршруты слушают только 127.0.0.1, проверяют точный путь и метод, запросы с браузерным Origin отклоняются. GET: /status, /logs?n=200. POST: /start, /stop, /restart. Принятие операции — 202, занято — 409, отсутствие токена — 403, неверный метод — 405. Итог операции проверяется через /status: RUNNING означает запущенный процесс, а не уже загруженный мир.

У supervisor есть stdin-команды start/stop/restart/status/quit при ручном запуске. Завершение supervisor запускает остановку принадлежащего ему ребёнка. При запуске кнопкой stdin сразу закрывается, управление остаётся через HTTP. Нормальное закрытие игрового окна оставляет supervisor в STOPPED для последующего /start. Чтобы полностью убрать фонового supervisor, завершите именно supervisorPid из /status штатным средством ОС; не убивайте все java-процессы.

## Пределы остановки и плана

По умолчанию cooperative restart ждёт штатного выхода до 15 секунд (сохранившиеся старые настройки не перезаписываются). Затем выполняется destroy, ожидание gracefulStopMs=2000 и при необходимости destroyForcibly с дополнительным ожиданием до 5 секунд. Это верхние пределы отдельных фаз, а не обещание рестарта за две секунды. Если дерево не удалось остановить, второй клиент не запускается. Принудительное завершение может прервать сохранение мира; для большого мира увеличьте cooperative-таймаут.

Supervisor периодически запоминает обнаруженных потомков и сохраняет их handles после выхода wrapper. Для Gradle автоматически добавляется --no-daemon, явный --daemon отклоняется. Общие Gradle daemon-процессы нельзя надёжно считать собственностью supervisor. Очень короткоживущие wrapper, успевающие породить и отвязать процессы между опросами, не покрываются гарантией: для строгого дерева ОС понадобятся Windows Job Objects/Linux cgroups. Нативная изоляция в этот патч не добавлена.

Никакие session.lock, блокировки мира, общие кэши и произвольные временные файлы не удаляются. Прибрать чужие блокировки безопасно без владения процессом нельзя. CDS/AppCDS, watcher, прогрев, изменения чанков и native image не добавлялись. Это ремонт фундамента шагов 1–5, существующей F9 и части механики остановки; следующие этапы требуют отдельных измерений. Время полной загрузки Minecraft здесь не измерялось, достижимость 2–3 секунд не заявляется.

## Проверки

verification/check-supervisor.py компилирует реальные production-классы JDK-only пакета и запускает настоящие JVM. Проверяет EOF, UTF-8/пробелы, env, методы/токен/пути HTTP, логи, 8 конкурирующих запросов, stop/start, завершение supervisor, timeout/force, ошибку исполняемого файла, занятый порт. ConfigChecks также проверяет повреждённые индексы команд, пределы порта, кавычки, Windows/Linux нормализацию wrapper и отказ от shell-метасимволов. Симуляция os.name проверяет только построение argv, не выполнение cmd.exe.

Здесь проверки выполнены на доступном JDK 17 (исходники supervisor совместимы с ним). Мод/встроенный bootstrap собираются Java 21. Полная Gradle-сборка и клиент Minecraft не выполнялись: нет Java 21 и готового NeoForge build environment. На данном хосте ProcessHandle.current().isAlive() возвращает false, /proc скрыт, поэтому успешный handoff и очистка потомков явно отмечены SKIP в логе. Отказ при недоступных ProcessHandle проверен. На обычном ПК тот же скрипт выполняет эти сценарии при доступных ProcessHandle. Нужна проверка Windows cmd.exe и игрового сохранения на вашем ПК; это не заменяется JDK-тестами.

Запуск из распакованного комплекта:

```powershell
$env:SUPERVISOR_TEST_JAVA = "$env:JAVA_HOME\bin\java.exe"
py verification\check-supervisor.py
```

После полной сборки проверьте, что JAR мода содержит mared/dev/supervisor-bootstrap.jar. Затем: активация не создаёт два окна одновременно; F9 из мира восстанавливает состояние; повторное F9 во время перезапуска не создаёт лишнюю игру; занятый порт не закрывает исходную игру; обычное закрытие окна не вызывает самопроизвольный запуск. При медленном сохранении увеличьте gracefulRestartWaitMs до проверки на ценном мире.
