# MaRed. Аудит серверного контура загруженной версии

База патча — архив `MaRed(2).zip`. Рабочая копия собрана из исходников и тестов архива. Версия проекта не повышалась.

## Файлы и связи

Индекс `SERVER_AUDIT_INVENTORY.csv` содержит 500 файлов: 370 Java, 117 Python и 13 C-заголовков и исходников. Учитывались пакеты сервера, Workspace и supervisor, утилиты и контроллеры Python, Windows Job. Для каждой строки указаны путь, число строк, вид проверки и явные локальные импорты или включения. Связи через Gradle, вызовы JVM по строковому имени, команды, сетевые DTO и файловые протоколы в этот список импортов входят только при наличии соответствующего импорта в коде.

Вручную прослежены следующие пути:

- Управление сервером: `tools/server104.py` → owner и lock в `inplace104.py` → запуск `batch124.py` и `windows_job.py` → статусы и подтверждения для Java-панели.
- Развёртывание: `automatic156.py` → очередь контроллера → `folder118.py`, `changes104.py` и `approval120.py` → инвентарь `FirstLaunchFiles` у игрового процесса.
- Восстановление и публикация: `prepared161.py`, `repair78.py`, `publication85.py`, `folder120.py` → журналы и указатели релизов.
- Подключение клиента: `session61.py`, `auth89.py` → файлы сеанса → `install70.py` и `rebind86.py` → проверка пакета → HTTPS-маршруты состояния и возобновление загрузки.
- Хранилище и редактор сервера: `PackageStaging`, `InstallJournal`, `ServerFiles156` → временные файлы, журнал, резервная копия и проверка актуальности сохранения.
- Supervisor: границы конфигурации `ServerProcessConfig`, наблюдение `ServerLifecycleView` и владение процессом `ServerProcessGuardian`.

## Исправленные дефекты

| № | Сценарий | Исправление |
|---|---|---|
| 1 | Python и Java расходились в проверке имени, регистра расширения и предельного числа JAR. | Согласованы правила инвентаря, установки и подготовки. Windows-зарезервированные имена, коллизии регистра и пустые JAR отклоняются. |
| 2 | Java дважды читал и хешировал каждый JAR при построении одного инвентаря. | Один хеш используется и при проверке записи, и при построении отпечатка инвентаря. |
| 3 | Переименование `a.jar` в `A.jar` могло пройти подготовку в виде двух путей, которые на Windows указывают на один файл. | Коллизия обнаруживается до записи журнала. |
| 4 | Неудачная запись подготовленных JAR оставляла неполную папку и блокировала повтор с тем же подтверждением. | Удаляется только принадлежащая операции папка до публикации журнала. |
| 5 | Неудачное первоначальное копирование релиза оставляло каталог задания и мешало повтору. | Импорт выполняется во временном каталоге с уборкой при отказе. |
| 6 | Два процесса подготовки могли одновременно выполнять операции одного задания. | Используется блокировка на идентификатор задания, а состояние читается внутри неё. |
| 7 | Двойной опрос состояния TLS мог пропустить ответ об отказе между чтениями. | Каждая итерация использует один снимок состояния. |
| 8 | Ошибка записи или синхронизации нового приватного файла оставляла неполный файл. | При отказе удаляется только файл, открытый данной операцией на эксклюзивное создание. |
| 9 | Два потребителя могли прочитать один файл сеанса, а очистка старого сеанса могла удалить новый файл. | Сеанс сначала присваивается переименованием, затем читается и удаляется под отдельным именем. |
| 10 | Повторное или одновременное подтверждение обновления могло перезаписать запись другого артефакта. | Подтверждение создаётся эксклюзивно. Формат UUID согласован с Java. |
| 11 | Часть локальных записей читалась без лимита после отдельного `stat`. | Предел применяется при чтении JSON, HMAC-записей, ключа подтверждений, BAT и двух публичных записей состояния. |
| 12 | Журнал Java выделял буфер из размера, прочитанного после внешней проверки файла. | Лимит и полнота чтения сверяются на открытом канале. |
| 13 | Повтор загрузки использовал постоянное временное имя, а ошибка проверки оставляла копию. | Каждая попытка использует собственный каталог. Активный архив заменяется после проверки. |
| 14 | HTTP-заголовки размера архива вычислялись до открытия файла. | Длина берётся с открытого потока, который обслуживает ответ. |
| 15 | Каталог настроек мог молча обрезаться по пределу сканирования. | При превышении предела возвращается явная ошибка. Каждый путь проверяется перед добавлением. |
| 16 | Открытый ранее редактор мог сохранять черновик для старого мира после изменения `level-name`. | Область доступа для черновиков пересчитывается. |
| 17 | Проверки перед сохранением настроек выполнялись под блокировкой одного объекта. Два экземпляра редактора могли записать разные изменения от одного снимка. | Записи MaRed сериализованы по каталогу сервера. Повторное сохранение со старой контрольной суммой отклоняется. |
| 18 | Набор истории сначала перечислял все файлы и мог прочитать запись без лимита после внешней проверки. | Перечисление и чтение ограничены до выделения буферов. |
| 19 | Проверка подмены истории иногда записывала исходные байты обратно и падала случайно. | Тест гарантированно меняет последнюю шестнадцатеричную цифру подписи. |

## Проверки и границы покрытия

- Базовая версия прошла 1 146 Python-тестов. После изменений прошли все 1 158 проверок доступного набора `verification/server59`.
- JDK 21 скомпилировал все 270 Java-файлов модуля Genesis Core. Парсер Java проверил 370 файлов выбранного контура. Python AST проверил все 117 файлов индекса.
- Отдельно прошли Java-проверки состояния панели, целей сервера, прав и обновления (192 проверки), а также сценарии инвентаря, смены мира, конкурентного сохранения и предела каталога на временных файлах.
- Gradle Wrapper не смог скачать Gradle 8.14.5 в этой среде. Полная Gradle-сборка, NeoForge, живые игровые сценарии и Windows Job требуют запуска в подходящей среде.

Это подтверждённая часть аудита. Индекс и автоматические проверки не являются ручной вычиткой каждого файла. Остаётся построчная проверка серверных Java-обработчиков Workspace, оставшихся веток supervisor, справочных сценариев и C-кода Windows Job. 50 отдельных подтверждённых дефектов и полное ручное покрытие пока не достигнуты.

## Второй проход по Workspace и supervisor

Вручную прослежены обработка приглашений, очередь публикации снимков, запись журнала Workspace, владение хранилищем и клиентским процессом, фоновое чтение истории и холодный запуск supervisor.

| Сценарий | Исправление |
|---|---|
| Исключение в обработчике ошибки могло остановить очередь снимков и оставить её в состоянии «задача запланирована». | Очередь продолжает обработку после ошибки уведомления. |
| Когда достигнут предел участников, отказ мог поглотить действующее приглашение. | Сервер проверяет текущий состав до погашения приглашения. После освобождения места действует то же приглашение. |
| Второе открытие Workspace в одном JVM могло снять блокировку первого объекта на POSIX при закрытии второго дескриптора. | Владение проверяется до открытия дескриптора. Отдельный JVM подтверждает, что блокировка осталась на месте после отказа. |
| Ошибка освобождения блокировки могла пропустить закрытие канала и оставить отметку владения в памяти. | Проводится вся очистка. Исходное исключение сохраняется. |
| Снимок Workspace, конфигурация supervisor и файл аргументов JVM могли вырасти после проверки размера. | Чтение ограничено фактически прочитанными байтами. Символические ссылки в этих путях отклоняются. |
| Регистрация и освобождение GameLease могли пересекаться. | Операции синхронизированы, отметка владения сохраняется до закрытия канала. |
| Исключение при передаче результата фонового чтения истории могло навсегда оставить статус READING. Отменённые запросы могли занимать очередь. | Ошибка переводит чтение в завершённое состояние. Отменённая задача удаляется из очереди там, где исполнитель поддерживает удаление. |
| При коллизии имени аргументов запуска очистка могла затронуть чужой файл. | Очистка охватывает только файл, успешно созданный текущей операцией. На POSIX права устанавливаются перед записью. |
| RuntimeFiles мог принять ссылку или точку перенаправления в пути к служебным файлам. | Компоненты пути проверяются перед использованием. |

Повторно прошли 1 158 Python-тестов. JDK 21 скомпилировал 270 исходников Genesis Core и 60 исходников supervisor и admission. В 13 отдельных Java-наборах прошли 2 779 проверок, включая конкуренцию двух JVM за одно хранилище, повторное использование приглашения после освобождения места и сбой передачи результата истории. Компилятор C11 проверил синтаксис трёх переносимых исходников Windows Job. Запуск нативного компонента на Windows, полная Gradle-сборка и сквозной сценарий NeoForge с несколькими клиентами остаются открытыми.

## Третий проход по цепочке обновления

| Участок | Исправление |
|---|---|
| Согласие и подписание решения | После потерянного ответа на POST установщик всё равно читает подписанное состояние и сверяет идентификатор подтверждения. |
| Передача управления от старого клиента | Установщик повторно читает команду, если завершение процесса пересеклось с записью COMMIT. Завершение без COMMIT отклоняется. |
| Первый вход и следующие обновления | Штатный установщик отправляет JOINED из общего цикла наблюдения. При потере ответа повтор сохраняет номер запроса. |
| Завершение раунда | Сервер закрывает раунд после подтверждённого входа всех участников. При сбое закрытие повторяется с работающим сервером. |
| Отмена | Предыдущая публикация восстанавливается до записи CANCELLED. Повтор очистки проверяет фактический набор модов и идентификатор операции. |
| Перезапуск | Контроллер сверяет READY с состоянием процесса и дочитывает итоговое подтверждение сохранения после выхода. |
| Очередь команд | Временный сбой ACK допускает повтор записи для команды из локального управления. Выданное удалённое разрешение не переносится на повтор после сбоя. |
| Фоновое продление выпуска | Для неизменного выпуска полная фоновая проверка выполняется раз в минуту вместо опроса каждые пять секунд. Перед фактическим продлением заново проверяются процесс и архивы. |

В прошедших 1 164 Python-тестах шесть новых целевых сценариев. JDK 21 собрал Genesis Core. Два процесса-стенда штатного обновления прошли установку через HTTPS, подтверждение COMMIT, запуск отдельного клиента и три попытки входа. Серверный стенд прошёл 126 проверок подписанной публикации, перехода с тремя участниками и восстановления. Клиентские и серверные события Minecraft моделируются. Проверка Windows Job и замер ускорения на выделенном игровом сервере ещё нужны.
