# MaRed / Genesis — staged-startup-13

Накопительный патч с backup/restore поверх 05–12. Уменьшает работу MaRed на пути загрузки: необязательный интерфейс создаётся по запросу, обслуживание кэшей ждёт готовности игры, а локальный мир после supervised restart входит с постепенным возвратом дальности.

## Как работает система

До входа в мир/готового меню остаются необходимые runtime-сервисы, persistent-скрипты и загрузка обнаруженных плагинов. Подготовка необязательного интерфейса и служебные файловые задачи разделены с этой работой.

- Если внешних MaRedPlugin нет, PluginLoader не запускает bootstrap реестров модулей, панелей и настроек. UI-ссылки вынесены в отдельный ленивый holder. Реестры панелей/настроек уже умеют подготавливаться при первом обращении. Если плагин найден, bootstrap выполняется до его конструктора и onLoad, как раньше: порядок регистрации сохраняется.
- На промежуточном TitleScreen при автоматическом возврате в мир/на сервер или локальном quickstart не создаётся кнопка MaRed и не читаются её настройки. На обычном меню и PauseScreen кнопка остаётся. Ошибка возврата, после которой открывается обычный TitleScreen, возвращает обычный UI.
- Хеширование direct-launch cache из 12 больше не стартует при mod_loaded одновременно с загрузкой игры. Оно ставится в ограниченную очередь обслуживания.
- Экспорт bitmap-шрифта перехода использует ту же очередь вместо отдельного параллельного потока.
- Очередь ждёт 1 секунду устойчивой готовности: доступны player+level либо обычное меню; overlay отсутствует. Промежуточный TitleScreen с ожидающим возвратом не считается готовностью. Потеря готовности сбрасывает ожидание и задерживает следующую задачу.
- Для локального возврата через supervisor профиль поэтапного входа из 07 теперь включён по умолчанию, если fastWorld.enabled не задан. На входе render/simulation ограничиваются максимум 4 чанками; через 2 секунды устойчивой готовности начинаются шаги восстановления по 2 чанка каждые 500 ms. Исходная дальность сохраняется в write-ahead journal. Явные изменения пользователя, recovery после сбоя и таймауты обрабатываются прежним кодом. Обычный запуск без supervisor этим новым default не меняется. Настройка fastWorld.enabled=false имеет приоритет.
- Очередь обслуживания также ждёт окончания восстановления дальности: подготовка видимого мира получает приоритет перед служебными задачами.
- Обслуживание выполняется последовательно на одном daemon-потоке с низким приоритетом. Идентификаторы задач не повторяются; очередь ограничена 8 задачами. Ошибка одной обычной задачи не блокирует следующую. При закрытии очередь очищается, executor прерывается; новые задачи не принимаются. Уже выполняющаяся файловая операция останавливается в тех местах, где её код учитывает interruption.

Это сокращает конкретную работу самого MaRed на пути основной загрузки. Здесь нет снимка памяти Minecraft, пропуска обязательных ресурсов, выгрузки произвольного NeoForge-мода или автоматического включения dynamic AppCDS. Последний требует подходящих JVM inputs; обычные dev classpath с непустыми каталогами не подходят. Поддержка opt-in AppCDS из прежних этапов сохраняется.

## Что можно ожидать по времени

Исходный пользовательский замер этапа 11: 23,925 с переход; launcher_gap 7,987 с, JVM→mod_loaded 8,328 с, ресурсы/меню 4,257 с, мир 2,227 с. Нового замера после 12 пока нет.

Изменения 13 прежде всего относятся к инициализации MaRed и периоду после mod_loaded. Они не доказывают ускорения первых 8,328 с JVM/NeoForge до конструктора MaRed. Величина выигрыша зависит от числа плагинов, стоимости GUI initialization, конкуренции фонового хеширования с загрузкой ресурсов и исходной дальности мира. Если эти операции на машине занимают мало времени, выигрыш тоже будет небольшим. Процент или результат 24→8 секунд пока не измерены.

Служебная работа всё равно выполняется после готовности: в отчёте она показана отдельно. Это перенос необязательных задач из времени ожидания, а не исчезновение всей стоимости. Первое обращение к отложенному интерфейсу может занять больше времени, чем при заранее подготовленном UI. При поэтапном входе первые секунды после возврата видимая дальность меньше обычной: дальние чанки появляются по мере возврата настроек. Измерение world_ready относится к доступному миру, а не к полной отрисовке всей исходной дальности.

Отключить новый default можно в `run/client/config/mared/dev/startup.properties`:

```properties
fastWorld.enabled=false
```

Существующий явный false сохраняется. Если он уже записан, патч не включает профиль поверх него. Для явного включения используй true.

## Установка

Закрой Minecraft и supervisor. Распакуй комплект и запусти `apply.cmd` для стандартного пути `%USERPROFILE%\Desktop\MappetPort\MaRed` либо:

```powershell
py .\patch\apply_changes.py "$env:USERPROFILE\Desktop\MappetPort\MaRed" --check
py .\patch\apply_changes.py "$env:USERPROFILE\Desktop\MappetPort\MaRed"
```

Установщик до записи проверяет все затронутые файлы, сохраняет backup, отказывается заменять неизвестные локальные правки. Для отката при закрытой игре:

```powershell
py .\patch\apply_changes.py "C:\путь\к\MaRed" --restore "C:\путь\к\MaRed-supervisor-backup-..."
```

Используй JDK 21. Из корня MaRed выполняй команды по отдельности; при ошибке остановись:

```powershell
.\gradlew.bat --stop
.\gradlew.bat clean --no-parallel
.\gradlew.bat build --no-parallel
.\gradlew.bat runClient
```

Нужно пересобрать основной мод и supervisor-bootstrap. Открытая старая JVM не обновляется от замены исходников.

## Проверка

1. После первого входа в мир подожди 3–4 секунды для фоновой подготовки direct-launch cache. Если нажать Apply сразу после входа, кэш ещё может быть не готов: тогда допускается Gradle fallback.
2. Примени одинаковое изменение в том же мире и проверь возврат, доступность persistent-скриптов и плагинов. Открой Studio/Settings: отложенные встроенные панели/вкладки должны появиться при первом обращении.
3. Проверь обычный TitleScreen/PauseScreen: кнопка MaRed остаётся; во время автоматического возврата промежуточное меню не подготавливает её.
4. После возврата и нескольких секунд ожидания выполни:

```powershell
py .\tools\restart_last.py .
```

К прежним полям добавлены:

| Поле | Значение |
|---|---|
| mod_to_resources_ready_ms | От mod_loaded до наблюдаемой готовности ресурсов/экрана; если отметки нет — null |
| mared_setup_ms.threading | Инициализация threading MaRed |
| mared_setup_ms.persistent | Загрузка persistent-скриптов |
| mared_setup_ms.plugins | Discovery/bootstrap/onLoad плагинов |
| mared_setup_ms.setup | Сумма трёх стадий клиентского setup |
| maintenance_ms.launch_cache | Проверка/сохранение кэша запуска после готовности |
| maintenance_ms.font | Экспорт шрифта после готовности |

mared_setup_ms — длительности, а не JVM uptime. Его части входят в общий период загрузки и не должны повторно прибавляться к total. resources_ready — наблюдаемая отметка на клиенте, а не полный profiler каждого ресурса. Очередь обслуживания может завершиться уже после world_ready; немедленный отчёт может ещё содержать null для maintenance.

При подходящем direct cache ожидаются launch_mode=direct_cache и fast_launch_reason=hit. При gradle причина остаётся в fast_launch_reason. Пришли полный компактный отчёт для сравнения с прежними 23,925 с. Пока нельзя оценить вклад переноса задач или подтвердить трёхкратное ускорение.

Не присылай direct-launch.properties, launch-seed-*.properties, direct-launch-arg-*.txt или supervisor.properties: там могут быть приватные аргументы и token.

## Проверки комплекта

16 наборов JDK-only/process/API-adapter тестов. Новые проверки: очередь с управляемыми часами/исполнителем, длительная загрузка без фоновых задач, quiet period и его сброс, потеря готовности перед исполнением, дедупликация/лимит/ошибка/закрытие; actual client gate с настоящим worker и doubles Minecraft; actual ServiceLoader с descriptor и plugin constructor-order check; пустой discovery без bootstrap; отключённый плагин; сохранение обязательного setup; supervised default/ordinary launch/явный false и восстановление дальности; обычный и временный TitleScreen/PauseScreen с doubles; новые поля отчёта. Предыдущие lifecycle/launch cache/overlay/trial/installer проверки сохранены.

Полная Gradle/NeoForge-сборка, Minecraft, headful Windows и новый performance benchmark здесь не выполнялись. Client/service API doubles не подтверждают binary compatibility. Successful parent handoff и descendants остаются SKIP, когда хост скрывает ProcessHandle metadata. Реальная сборка требует JDK 21; автономные проверки выполнялись на Linux/JDK 17.
